# Architecture: Signpost Checklist Redesign

Cites `01-REQUIREMENTS.md` (this sprint) and the archived mechanism at
`archive/first-turn-contract-enforcement/` (prior implementation being replaced — trigger-surface
plumbing and transcript-parsing primitives are reused from it verbatim where noted below).

**Note on schema language:** this repo's hook layer is Python (`scripts/*.py`, Stop-hook stdin/JSON
contract), not TypeScript/React. Schemas and signatures below are expressed as Python
`dataclass`/`TypedDict` and function signatures, matching the existing codebase's actual
conventions (`first_turn_contract_probe.py`) rather than the skill template's TS default.

---

## 1. Governing Design Constraint (restated, binding)

Per the archived mechanism's postmortem and this task's instructions: a check may only test
words the hook **controls** (a forced literal label/syntax the agent is instructed to reproduce
exactly) or **observes** (content copied verbatim from elsewhere in the same reply, or IDs that
exist verifiably in the transcript). No check in this design infers a *concept* from open-ended
phrasing. Every check below is one of:

- exact string equality (row label == Signpost line, byte-for-byte after list-marker stripping)
- membership in a small forced vocabulary (`- [ ]` / `- [x]`, an exact evidence-field syntax,
  the exact literal `unverified`)
- existence lookup against transcript structure (`tool_use_id` present in a completed tool call)

None of these require guessing what an agent's free prose "means."

### 1a. Division of Responsibility — Agent Authors, Hook Verifies

**A Stop-hook can only block or allow a turn already emitted; it cannot author text into the
agent's own reply.** Every checklist row in the Pillar section is therefore written by the AGENT,
not generated by the hook. The hook's entire job is to read the reply the agent already produced
and check it — nothing in this mechanism writes into the agent's reply.

Concretely, in every turn where this mechanism is gated on:

1. The **agent** copies each Signpost claim line verbatim into its own Pillar section as one
   checklist row (per the forced syntax in §5.3) — this satisfies the "copy verbatim" intent
   behind the Signpost/Pillar convention (US-1's underlying goal), performed by the agent, because
   only the agent can author its own reply.
2. The **hook** (`evaluate_checklist`, §5.4) then verifies those rows: it checks that every
   Signpost line has a matching row, that each row's declared status is honest and, where the row
   claims verification, that the claim is backed by a real `tool_use_id` found in the transcript.

The hook never infers, normalizes, or writes a row on the agent's behalf. Any architecture
language elsewhere in this document that could be read as "the hook copies/generates rows" (e.g.
§10's requirements-coverage table) refers to this verification role, not authorship — flagged
explicitly here to remove that ambiguity. This is a clarification of an already-established
project fact (Pillar ownership is always the agent's, never the hook's), not a new design
decision.

## 3. Data Schemas

```python
from dataclasses import dataclass
from typing import Optional

@dataclass(frozen=True)
class SignpostLine:
    """One verbatim claim line extracted from the Signpost section, in source order."""
    text: str           # content after list-marker stripping, byte-identical to source
    raw_line: str        # full original line (for quoting in FAIL reasons)

@dataclass(frozen=True)
class PillarRow:
    """One checklist row parsed from the Pillar section, in source order.
    Authored entirely by the agent (§1a) — this dataclass is the hook's parsed *read* of that
    text, never something the hook writes."""
    label: str                     # content between the checkbox and the forced status suffix
    status: str                     # forced literal: "verified" or "unverified" — see §5.3
    tool_use_id: Optional[str]      # set only when status == "verified"; always None otherwise
    raw_line: str

@dataclass(frozen=True)
class QualifyingToolCall:
    """A completed (tool_use + matching tool_result present), non-excluded tool call
    preceding the current turn. The archived probe's `_collect_qualifying_tool_calls`
    (archive/first-turn-contract-enforcement/scripts/first_turn_contract_probe.py:474-503) does
    NOT produce this shape as-is: it returns `(name, input)` tuples and drops `tool_use_id`
    entirely (it was never needed for the archived C3 subject-match check). This dataclass
    requires `tool_use_id`, which rule 4 (§5.4) needs to look up a claimed ID. §5.1 specifies
    the required extension: capture `tool_id` alongside `(name, input)` in the collection loop
    and include it in each returned item."""
    tool_use_id: str
    name: str
    tool_input: dict

@dataclass(frozen=True)
class RowViolation:
    kind: str            # one of: "missing", "duplicate_label", "stray_prose", "false_claim",
                          # "duplicate_id", "malformed_signpost" (§5.4 rule 0a), "unmatched_row"
                          # (§5.4 rule 7)
    signpost_text: Optional[str]   # set for "missing"
    row: Optional[PillarRow]        # set for "false_claim" / "duplicate_id" / "unmatched_row" /
                                     # "duplicate_label"
    line_text: Optional[str]       # set for "stray_prose" — the raw offending line, so
                                     # build_reason() can quote it per §4's contract

@dataclass(frozen=True)
class EvaluationResult:
    decision: str                 # "block" | "allow"
    violations: list              # list[RowViolation], empty on allow
    signpost_heading_absent: bool  # True only for the §5.4 rule-0 fail-closed case (§6 edge case)
    reason: Optional[str]         # human-readable, built from violations; None on allow
```

## 4. API Contracts

```python
def extract_signpost_lines(text: str, signpost_idx: Optional[int], pillar_idx: Optional[int]) -> list[SignpostLine]:
    """Lines in the Signpost section (between signpost_idx and pillar_idx, or end-of-text if
    pillar_idx is None) that match the markdown list-item shape (`-`, `*`, `+`, or `N.` marker).
    Non-list-item lines inside the section (blank lines, prose continuation) are not claim
    lines and are skipped — the claim unit is one list item, mirroring how the archived
    mechanism's Signpost/Pillar convention was authored in practice.
    Returns [] if signpost_idx is None (no Signpost heading) — callers MUST treat that case via
    §5.4 rule 0 (fail-closed block on a gated turn), not as "zero rows required." See §6 edge
    case table for the distinction between this case and a present-but-empty Signpost section.
    Also returns [] when the Signpost heading IS present but the section contains any non-blank
    text with zero matching list-item lines (e.g. a claim written as one prose sentence instead
    of a list item) — this is structurally indistinguishable from a truly empty section by this
    function's return value alone. Callers MUST NOT treat every empty `[]` result the same way:
    `evaluate_checklist` (§5.4) takes a separate `signpost_section_has_content: bool` flag to
    distinguish "genuinely nothing to verify" (zero-rows-required allow) from "claims exist but
    were written in a shape this parser can't recognize" (malformed-claims fail-closed block,
    §5.4 rule 0a). **`signpost_section_has_content` includes trailing content on the Signpost
    heading line itself.** The archived heading regex
    (`_SIGNPOST_PILLAR_HEADING_RE`, archive/first-turn-contract-enforcement/scripts/
    first_turn_contract_probe.py:48-51) matches a heading with prose on the same line
    (`Signpost: I verified the build and the tests.`), so "the section" is not just the lines
    strictly *between* the heading and the next heading — it is that span PLUS whatever text
    follows the heading label (`Signpost:` / `Pillar:`, case-insensitive, first colon) on the
    heading line itself, with the label stripped. A reply with only
    `Signpost: I verified the build and the tests.` and nothing beneath it therefore has
    `signpost_section_has_content = True` (non-blank trailing content on the heading line) and
    `signpost_lines = []` (no list-item line matched anywhere), which is rule 0a's fail-closed
    case, not a zero-rows-required allow. This closes the evasion of moving prose up onto the
    heading line to dodge rule 0a."""

def extract_pillar_rows(text: str, pillar_idx: Optional[int], section_end_idx: int) -> list[PillarRow]:
    """Lines in the Pillar section matching the forced checklist-row syntax (§5.2, §5.3), each
    parsed by `parse_checklist_row_line`. Lines in the Pillar section that do NOT match the
    syntax (including a row whose checkbox/label is present but whose status suffix is missing
    or malformed) produce no PillarRow — such a line is not parsed as evidence of anything, and
    the Signpost line it might have been attempting to satisfy is therefore reported as
    `"missing"` (§5.4 rule 1). Correction: this alone does NOT enforce "no free-form prose in
    Pillar" — a non-conforming line simply not counting as a row means the corresponding
    Signpost claim is reported missing; it does not flag the stray non-conforming line itself,
    which by itself is tolerated silently. `extract_pillar_rows` therefore also returns the raw
    non-blank lines in the Pillar section that failed to match the forced syntax (a separate
    `list[str]`, `unparsed_lines`), so `evaluate_checklist` can flag each one explicitly under
    §5.4's new stray-prose rule (rule 1b) rather than only inferring the gap indirectly through
    a missing-row report.

    **Pillar-section span and the heading line, resolved.** The archived slice this function's
    section-boundary logic is derived from
    (archive/first-turn-contract-enforcement/scripts/first_turn_contract_probe.py:674-683) builds
    `pillar_section_text` as `"\n".join(lines[pillar_idx:section_end])` — the Pillar **heading
    line itself is included** in the section span, not excluded. `extract_pillar_rows` and
    `unparsed_lines` follow that same inclusion, with one explicit carve-out: the heading line's
    own label (`Pillar:`, case-insensitive, up to and including the first colon) is stripped
    before the line is considered for row-parsing or stray-prose classification — the label text
    is never itself treated as a row or as stray prose, so a bare `Pillar:` heading with nothing
    else on the line does not self-flag. Any trailing content AFTER the label on that same heading
    line (e.g. `Pillar: all verified, trust me`) IS included in the line passed to
    `parse_checklist_row_line` / stray-prose classification, mirroring the Signpost-side handling
    in `extract_signpost_lines` above — a checklist row or free-text claim placed on the heading
    line itself is neither a silent free pass nor exempt from rule 1b; it is evaluated exactly as
    if it were a normal line inside the section. This closes both the ambiguity over whether the
    heading line is in `unparsed_lines` (it is, label-stripped) and the evasion of writing
    `Pillar: all verified, trust me` to bypass rule 1b."""

def parse_checklist_row_line(raw_line: str) -> Optional[PillarRow]:
    """Regex match against the forced row syntax (§5.3). None if the line doesn't match the full
    shape, including the required, forced status suffix — `(verified: tool_use_id=<id>)` or the
    exact literal `(unverified)`. A line with neither suffix is not a row at all."""

def collect_qualifying_tool_calls(records: list[dict], current_turn_index: Optional[int]) -> list[QualifyingToolCall]:
    """Extends the archived probe's `_collect_qualifying_tool_calls` (same tool_use/tool_result
    correlation, same TodoWrite exclusion) with one additive change: also capture `tool_id` into
    each returned item, so the result can be wrapped as `QualifyingToolCall(tool_use_id=tool_id,
    name=name, tool_input=input)` — the archived function itself returns `(name, input)` tuples
    with `tool_use_id` discarded and cannot be called unmodified. See §5.1."""

def evaluate_checklist(
    signpost_lines: list[SignpostLine],
    pillar_rows: list[PillarRow],
    qualifying_calls: list[QualifyingToolCall],
    signpost_heading_present: bool,
    signpost_section_has_content: bool,
    pillar_unparsed_lines: list[str],
) -> EvaluationResult:
    """Pure function, no I/O. Implements §5.4's evaluation rules, including rule 0's fail-closed
    behavior when `signpost_heading_present` is False on a gated turn, rule 0a's fail-closed
    behavior (`RowViolation(kind="malformed_signpost", ...)`) when the Signpost section — heading
    line's trailing content included, per §4's `extract_signpost_lines` — has non-blank content
    but zero parsed claim lines (`signpost_section_has_content` True, `signpost_lines` empty),
    rule 1b's stray-prose violation for each entry in `pillar_unparsed_lines`, and rule 7's
    `unmatched_row` handling (any `PillarRow` with no matching `SignpostLine` is still run through
    rules 3–5 and additionally flagged `unmatched_row`)."""

def build_reason(result: EvaluationResult) -> str:
    """One sentence per violation, concatenated — same style as the archived probe's
    build_reason, quoting the exact Signpost/Pillar line text involved. When
    `signpost_heading_absent` is True, the reason states that plainly (§5.4 rule 0) rather than
    listing per-line violations, since there are none to list."""

def run(stdin_data: dict) -> None:
    """Top-level entry point, same stdin contract, same stop_hook_active / queue-marker /
    first-turn gating as the archived probe's `run()` — see §5.1, unchanged."""
```

## 5.3 New: forced checklist-row syntax

The agent (§1a) must write each Pillar row in exactly one of these two forms — both are forced,
control-or-observe literals; there is no third, free-form option:

```
- [x] <verbatim Signpost line text> (verified: tool_use_id=<id>)
- [ ] <verbatim Signpost line text> (unverified)
```

The second form is the explicit, honest disclosure path required by US-2/Intake: an agent that has
not verified a claim writes the literal word `unverified` — it is never treated as a violation on
its own (§5.4 rule 2). This preserves control-or-observe: `unverified` is a forced literal the
agent must reproduce exactly, not free text explaining why.

```python
import re

_PILLAR_ROW_RE = re.compile(
    r"^\s*[-*+]\s*\[( |x|X)\]\s*(.*?)\s*"
    r"(?:\(verified:\s*tool_use_id=([A-Za-z0-9_\-]+)\)|\((unverified)\))\s*$"
)
```

- Group 1: checkbox state (`" "` unchecked, `"x"`/`"X"` checked). Cosmetic only — §5.4's rules key
  off the forced status suffix (group 3 vs. group 4), not the checkbox glyph, so a checkbox/suffix
  mismatch (e.g. `[x]` paired with `(unverified)`) is not separately flagged; this is a known,
  low-severity gap explicitly out of scope for this build (no requirement addresses it).
- Group 2: the row label — must equal some `SignpostLine.text` **exactly** (byte-for-byte, both
  sides trimmed of surrounding whitespace per §5.4's normalization note) for the row to count as
  satisfying that Signpost line. This is the "copy verbatim" requirement (§1a) enforced as string
  equality, not paraphrase-detection.
- Group 3: the `tool_use_id`, present only when the `(verified: tool_use_id=...)` suffix matches —
  sets `PillarRow.status = "verified"`.
- Group 4: the literal `unverified`, present only when the `(unverified)` suffix matches — sets
  `PillarRow.status = "unverified"` and leaves `PillarRow.tool_use_id = None`.
- **Exactly one** of the two suffix alternatives must match, or the whole line fails to match at
  all (`parse_checklist_row_line` returns `None`) — there is no third, unsuffixed row shape.

This is a **controlled** syntax (the hook dictates the exact shape; the agent is instructed to
reproduce it) — not an inferred concept. `tool_use_id` values are real UUIDs Claude Code assigns
to `tool_use` blocks in the transcript; an agent cannot self-report a plausible-looking evidence
claim, because a fabricated ID will not exist in `qualifying_calls` (§5.4 rule 3).

**Resolving 05-REVIEW Q-3/A-7 (agent-side `tool_use_id` lookup): FEASIBLE, confirmed live.** A
`tool_use_id` is not automatically visible to the agent in a normal reply — it must be actively
looked up. This is done the same way the hook itself already does it (`load_transcript_records`,
§5.1): the agent reads its own current session transcript file (the JSONL under
`~/.claude/projects/<project>/*.jsonl`, most recently modified) and searches backward for the most
recent `tool_use` block matching the call it wants to cite, to read that block's real `id` before
writing a `(verified: tool_use_id=<id>)` row. This is an active lookup step the agent must perform,
not something it already has in context — it must be stated explicitly to the agent as part of the
Pillar-authoring instructions (§1a), since without it an agent has no way to produce a real ID and
would be forced into either fabrication (caught by rule 4) or defaulting to `(unverified)` even
when verification did happen. **Delivery flag:** this lookup step is agent-facing syntax/behavior,
not hook logic — it belongs in whatever Slice delivers the agent-facing instructions for writing
Pillar rows (Slice 5 per 04-ROADMAP.md), not in the probe implementation slices. Route a small
addition there: document the transcript self-lookup step as part of the instructions an agent
follows when authoring a `(verified: ...)` row.

## 5.4 Evaluation rules (`evaluate_checklist`)

**Rule 0 — Signpost heading absent (fail-closed).** If `signpost_heading_present` is False (the
reply has no Signpost heading at all) on a turn this mechanism is gated on, the result is an
immediate `decision = "block"`, `signpost_heading_absent = True`, with no per-line rules below
evaluated. **This is a deliberate, new scope decision for this sprint, not an inherited one:** the
archived mechanism's own decision flow explicitly *allowed* a no-Pillar/no-Signpost turn (its
ALLOW4 branch) — rule 0 is a real behavior change relative to that archived flow, not a reuse of
its logic or citation. The rationale stands on its own terms: the hook only fires when the
session-queue briefing marker was injected (§5.1) — i.e. only when a Signpost-type claim is
already expected for this turn — so a missing heading in that situation is a silent bypass of an
expected contract (an agent could omit Signpost entirely to skip the whole check), which this
design chooses to treat as a violation rather than vacuous success. **This diverges from the
archived mechanism's own allowed behavior; it is not carried forward on the strength of
prior-mechanism precedent.** Confirmed by Danny (2026-09-07): tested against this sprint's own
North Star intent — closing the evasion channels the archived mechanism's permissive design left
open — blocking here points the same direction as that intent rather than diverging from it, so
the stricter behavior stands as designed. This is distinct from the case below where the heading
**is**
present but the section contains zero claim lines, which is not a bypass (there is genuinely
nothing to verify) and is handled separately.

**Rule 0a — Signpost heading present, section has content, zero claim lines parsed (fail-closed).**
If `signpost_heading_present` is True and `signpost_section_has_content` is True (per §4's
`extract_signpost_lines` definition: the text between the Signpost heading and the next heading,
PLUS any trailing content on the Signpost heading line itself after the `Signpost:` label is
stripped, after stripping blank lines, is non-empty) but `signpost_lines` is empty (no line matched
the list-item shape §4 requires), the result is an immediate `decision = "block"` with a
`RowViolation(kind="malformed_signpost", signpost_text=None, row=None)` (§3) stating the Signpost
section is malformed (claims appear to exist as prose — including prose written directly on the
heading line — but were not written as list items) — the same fail-closed treatment as rule 0, for
the same reason: content is present but not in the checkable shape, so it is not "nothing to
verify," it is "something unverifiable by this mechanism's rules." Purely structural (non-blank-
content presence vs. zero-line-match count) — no new constant. Only when the section is truly empty
(no non-blank content anywhere, including the heading line's trailing content) does the legitimate
zero-rows-required allow (below rule 6) apply. This closes the evasion of writing
`Signpost: I verified the build and the tests.` with nothing beneath it to obtain a
zero-rows-required allow instead of rule 0a's block.

Otherwise, for each `SignpostLine` in `signpost_lines`, find `PillarRow`s whose `label == line.text`
exactly (both sides compared after `.strip()`, applied symmetrically on the Signpost-line and
Pillar-row-label side — resolving the whitespace-symmetry gap: `extract_signpost_lines` and
`parse_checklist_row_line` both strip leading/trailing whitespace from the compared text before
storing it, so a row differing from its Signpost line only by trailing/leading spaces still counts
as a match):

1. **No matching row found** (including a Pillar line that failed to parse under §5.3's forced
   syntax — such a line produces no `PillarRow` at all, so it can never match) →
   `RowViolation("missing", signpost_text=line.text)`.
1a. **More than one `PillarRow` matches the same `SignpostLine.text`** (e.g. one `(unverified)` row
   and one `(verified: tool_use_id=...)` row both carrying the identical label) → each matching row
   for that line produces `RowViolation("duplicate_label", row=row)`; neither row is evaluated
   further under rules 2–5 for that line. Consistent with rule 0's fail-closed precedent: this is a
   structural count check (how many rows matched a line — a fact directly readable off the parsed
   structures), not text inference, so it needs no new constant. Only a single-match case proceeds
   to rules 2–5 below.
1b. **Any entry in `pillar_unparsed_lines`** (a non-blank line inside the Pillar section that does
   not match the forced row syntax, §5.3) → `RowViolation("stray_prose", row=None, line_text=<the
   raw line>)` for each such
   line, in addition to whatever "missing" violation (rule 1) results from the Signpost line it may
   have been attempting to satisfy. This closes the gap where free-form prose in the Pillar section
   was tolerated silently alongside valid rows (§4's `extract_pillar_rows` correction): a
   non-conforming line is now itself flagged as a violation, not just indirectly implied by a
   missing row. Purely structural (line present, does not match forced syntax) — no new constant,
   no inference about what the prose *means*.
2. **Matching row found, `status == "unverified"`** → no violation. This is the honest,
   forced-literal non-verification path (§5.3) — it is *always* allowed and is never itself a
   FAIL. This is the corrective for the archived mechanism's original purpose: an agent must be
   able to truthfully say "I have not verified this" without that disclosure being penalized.
3. **Matching row found, `status == "verified"`, but `tool_use_id` is `None`** →
   `RowViolation("false_claim", row=row)`. (Structurally this should not occur given §5.3's regex,
   since the `"verified"` status only ever arises from a match that captured group 3 — kept as a
   defensive rule in case of future syntax changes.)
4. **Matching row found, `status == "verified"`, `tool_use_id` set, but no `QualifyingToolCall` in
   `qualifying_calls` has that `tool_use_id`** → `RowViolation("false_claim", row=row)` — satisfies
   US-2 AC2 ("claims a tool call that does not exist in the transcript" → treated as an unbacked,
   false claim, not allowed to pass on the strength of the claim alone).
5. **Matching row found, valid `tool_use_id`, but that same `tool_use_id` was already claimed by
   an earlier `"verified"` row in this evaluation** → `RowViolation("duplicate_id", row=row)`.
   **"Earlier" is resolved as evaluation order, not source/reply order** — the order rows are
   actually processed by `evaluate_checklist()` (the per-Signpost-line matching pass, rules 1-6,
   followed by the rule 7 residue pass over unmatched rows), not the order their lines appear in
   the agent's raw reply text. This was flagged as ambiguous during an independent diagram
   cross-check (2026-09-07) — resolved here rather than left implicit, since a row appearing
   earlier in the reply but evaluated later (e.g. an unmatched row, evaluated in the rule 7 pass
   after all matched rows) would otherwise be read two different ways.
   *Design addition beyond the literal ACs* — flagged explicitly for review: without this, one
   real tool call could trivially "back" every row regardless of relevance, which would satisfy
   AC-2's literal wording ("traceable to an actual tool call") while defeating the mechanism's
   evident purpose (each verified claim independently checked). `"unverified"` rows carry no
   `tool_use_id` and are never subject to this rule. This is a mechanical uniqueness constraint (no
   threshold, no inferred text-matching) — if a reviewer decides it exceeds requirement scope,
   delete rule 5; nothing else in the design depends on it.
6. **Every Signpost line has exactly one matching row (per rule 1a — no duplicate-label case), and
   that row is either `"unverified"` or a uniquely-claimed, transcript-verified `"verified"` row** →
   no violations, `decision = "allow"`.

If the Signpost heading **is** present but `signpost_lines` is empty (zero list-item lines in the
section) → zero rows required, no violation solely from absence — this is the "nothing to verify"
case, distinct from rule 0's "heading missing entirely" case (see rule 0's note above).

7. **A `PillarRow` (successfully parsed under §5.3's forced syntax) has no matching `SignpostLine`**
   (an "unmatched row" — a row present in the Pillar section whose label does not equal any
   `SignpostLine.text`) → the row is NOT silently ignored. It is subject to rules 3–5 exactly as a
   matched row would be (unbacked `verified` claim → `RowViolation("false_claim", row=row)`;
   reused `tool_use_id` → `RowViolation("duplicate_id", row=row)`), and in addition always produces
   `RowViolation(kind="unmatched_row", signpost_text=None, row=row)`, whether its status is
   `verified` or `unverified`. This closes the gap where a syntactically valid but unmatched row
   (e.g. `- [x] all verified, trust me (verified: tool_use_id=toolu_fake)`) passed rules 2–5
   untouched because those rules previously only ran on rows matched to a Signpost line — an
   unmatched row is exactly the shape of a self-reported, unchecked verification claim written in
   the trusted syntax, which NS SC2 ("every row's status is tool-call-backed") requires this
   mechanism to catch regardless of whether the row happens to correspond to a real Signpost line.

`decision = "block"` if `violations` is non-empty (or rule 0 fired); `reason = build_reason(result)`.

## 6. Patterns

| Pattern | Usage | Rationale |
|---|---|---|
| Pure-function core + thin I/O wrapper | `evaluate_checklist()` takes parsed structures, no stdin/transcript access | Matches the archived probe's testability pattern; the acceptance-criteria table maps directly onto `evaluate_checklist` unit tests without transcript fixtures. |
| Fail-open on any exception, fail-closed on a missing expected section | `main()`'s outer try/except is unchanged fail-open (archived probe); §5.4 rules 0/0a are distinct, deliberate fail-closed rules for the specific cases of an absent or malformed Signpost section on a gated turn | A hook that crashes into a block on its own bugs is worse than no hook (fail-open). But a hook that silently allows the exact input shape it exists to check (no Signpost, or unparseable Signpost, at all) just because that shape produces zero required rows is a permissive-fallback bypass. This is a deliberate, new scope decision for this sprint, not a reuse of the archived mechanism's citation — the archived flow's own ALLOW4 branch explicitly allowed a no-Signpost/no-Pillar turn, so rule 0/0a diverge from it — confirmed by Danny (2026-09-07) as still pointing at this sprint's North Star intent, not an inherited justification (see §5.4 rule 0). |
| Agent authors, hook verifies | §1a; §5.3 forced row syntax written by the agent; §5.4 evaluated by the hook | A Stop-hook cannot write into an already-emitted reply — only block or allow it. Any design that has the hook "generate" text is not implementable; this pattern is the only feasible division of labor and is stated explicitly to close G-1. |
| Reuse over reimplementation for unrelated logic | §5.1 items imported/copied verbatim | The trigger-surface and tool-call-correlation code was never the source of the archived mechanism's failures (only the subject-inference layer was) — re-deriving it introduces new bugs for no requirement benefit and duplicates already-battle-tested code paths. |
| String-equality matching for row labels | §5.3, §5.4 | Directly satisfies the governing principle (§1) — no fuzzy/paraphrase matching, no regex tuned against guessed phrasing. |
| Forced ID-citation syntax over free-text evidence | §5.3–5.4 | Existence-lookup against real transcript structure is the only evidence type that cannot be self-reported; any free-text "evidence" field (file:line, command output) reopens exactly the self-report gap US-2 exists to close. |
| Forced literal for honest non-verification | §5.3's `(unverified)` suffix; §5.4 rule 2 | Preserves control-or-observe while still allowing honest disclosure: the agent reproduces an exact literal, not free prose, so the hook never has to infer whether a disclosure "counts" — it only checks the literal is present. This is the direct fix for what the archived mechanism's C2 check existed to protect. |

### Anti-Patterns (Do Not Use)

- Any regex that tries to detect an admission/disclosure *concept* in free Pillar prose (the C2/C3
  admission-detection failure mode) — explicitly forbidden by the governing principle and by this
  sprint's Out of Scope. The `(unverified)` literal (§5.3) is the sanctioned replacement: a forced
  label, not an inferred concept.
- Subject-extraction + fuzzy target matching (the deleted §5.2 machinery) — do not resurrect it as
  a way to "double-check" `tool_use_id` relevance. If relevance-of-evidence-to-claim ever becomes a
  real requirement, it needs its own Intake/spec cycle, not a bolt-on here.
- Any numeric similarity/confidence threshold for row-label matching (e.g. "90% string match
  counts as verbatim") — labels are exact-equality only; a near-miss is a `"missing"` violation,
  full stop. Introducing a fuzzy threshold would reintroduce an unsourced-number problem this
  design has no need for.
- Treating "no Signpost heading" the same as "Signpost heading present, zero lines" — the former
  fail-closed-blocks (rule 0), the latter is a legitimate zero-rows-required allow. Collapsing the
  two reopens the no-Signpost bypass this redesign explicitly closes.

## 9. Validation Approach (per task constraint — no self-written-fixture certification)

`evaluate_checklist()` is a pure function over already-parsed structures and can be unit-tested
directly against the requirements' own Given/When/Then AC table without transcript data.

The two functions that touch real transcript shape — `collect_qualifying_tool_calls()` (reused
per §5.1a with the additive `tool_use_id` capture; its correlation logic is already validated
against real transcripts in the archived sprint) and
`parse_checklist_row_line()`/`extract_signpost_lines()` (new, but pure regex over reply text, not
transcript structure) — carry the actual risk of false-negative/false-positive on real data. Per
the task constraint, before this ships, the new row/line parsers must be run against a sample of
real `~/.claude/projects/*/*.jsonl` first-turn replies (once some exist in the new Signpost/
checklist format) to confirm the forced syntax survives real agent output, not a hand-authored
fixture. This is a forge/verification-phase task, not resolved further at the architecture stage.
